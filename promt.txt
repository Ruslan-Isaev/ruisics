# Задача: комплексная доработка Android-приложения для работы с ICS

Ты работаешь с существующим Android-приложением на Kotlin, предназначенным для импорта, экспорта и управления календарными событиями в формате ICS.

Твоя задача — доработать существующий проект, сохранив работоспособность имеющихся функций, архитектуру там, где она удачна, и совместимость с текущими данными пользователя.

**Не переписывай приложение с нуля и не меняй технологический стек.** Сначала изучи проект, затем составь план изменений и приступай к реализации. Не ограничивайся рекомендациями, псевдокодом или созданием макетов: необходимо реализовать функциональность в исходном проекте.

## 1. Обязательные правила работы

1. В начале изучи структуру проекта, используемые библиотеки, архитектуру, существующие экраны и механизмы работы с ICS и системным календарём Android.
2. Не удаляй и не ломай существующие функции импорта, экспорта и управления событиями.
3. Не заменяй существующие реализации новыми без необходимости.
4. Сохраняй совместимость с текущими версиями Android, `minSdk` и другими ограничениями проекта.
5. Используй существующие архитектурные подходы проекта, если они не мешают выполнению требований.
6. Новые функции должны быть разделены на логические модули и не должны превращать один класс в огромный файл со всей бизнес-логикой.
7. Не добавляй сторонние библиотеки без необходимости. Для каждой новой зависимости проверь актуальную версию, лицензию и совместимость с проектом.
8. Не оставляй фиктивные обработчики кнопок, TODO вместо реализации или демонстрационные данные вместо рабочих функций.
9. Не выполняй опасные операции с календарём без явного подтверждения пользователя.
10. После изменений собери приложение, исправь ошибки компиляции и запусти доступные тесты.

## 2. Модульная система языков

Необходимо реализовать систему локализации, позволяющую добавлять новые языки отдельными JSON-файлами, не изменяя бизнес-логику приложения.

### Требования

- Переводы интерфейса должны храниться отдельно от исходного кода.
- Каждый язык представляет собой самостоятельный JSON-файл.
- Добавление нового языка должно сводиться к добавлению файла и, при необходимости, регистрации его метаданных.
- Не должно требоваться изменять Kotlin-код для каждого нового языка.
- Язык приложения выбирается пользователем в настройках.
- Предусмотри режим автоматического выбора языка системы.
- Выбранный пользователем язык должен сохраняться после перезапуска приложения.
- После переключения языка интерфейс должен обновляться корректно.
- Все надписи, меню, кнопки, диалоги, сообщения об ошибках, уведомления внутри приложения и настройки должны использовать систему локализации.
- Не допускай смешивания переведённого интерфейса с жёстко прописанными строками.
- Если для выбранного языка отсутствует перевод отдельного ключа, используй английский язык как резервный. Если английского перевода тоже нет, используй безопасное отображение ключа или понятное значение по умолчанию и сообщай о проблеме в режиме разработки.
- Предусмотри параметры форматирования строк и корректное форматирование дат, чисел и времени с учётом локали.
- Не используй машинный перевод непосредственно во время работы приложения.

### Формат файлов

Пример:

`app/src/main/assets/locales/ru.json`

```json
{
  "meta": {
    "code": "ru",
    "name": "Русский",
    "nativeName": "Русский",
    "direction": "ltr"
  },
  "strings": {
    "app.name": "Календарный помощник",
    "menu.settings": "Настройки",
    "menu.shifts": "Планировщик смен",
    "menu.holidays": "Праздники",
    "settings.language": "Язык приложения",
    "settings.theme": "Тема оформления",
    "action.cancel": "Отмена",
    "action.confirm": "Подтвердить",
    "action.delete": "Удалить",
    "error.generic": "Произошла ошибка"
  }
}
```

Создай полноценный английский и русский наборы переводов для всех строк приложения.

Этот JSON — пример схемы, а не полный перечень обязательных строк.

### Архитектура

Создай отдельный компонент, отвечающий за:

- обнаружение доступных языковых файлов;
- проверку их структуры;
- загрузку и кэширование переводов;
- получение строк по ключам;
- подстановку параметров;
- резервные переводы;
- переключение активного языка;
- сохранение пользовательского выбора.

Не привязывай бизнес-логику приложения к конкретному языку.

Учитывай ограничения Android: ресурсы в `assets` не являются автоматически обнаруживаемыми модулями, поэтому реализуй явный механизм обнаружения файлов, например по манифесту или списку файлов, с проверкой корректности данных.

Если проект использует Jetpack Compose, обеспечь реактивное обновление интерфейса при смене языка. Если используется XML, адаптируй механизм к существующей архитектуре.

## 3. Модульная система наборов праздников

Реализуй возможность подключения отдельных наборов праздников через JSON-файлы.

**Главное требование: праздники и их переводы должны быть отделены от бизнес-логики приложения.**

Новый набор праздников должен подключаться добавлением файлов данных без необходимости изменять Kotlin-код, создавать новые экраны или пересобирать бизнес-логику.

### Организация файлов

Используй отдельную директорию, например:

`app/src/main/assets/holiday_packs/`

Каждый набор должен иметь собственную директорию:

```text
holiday_packs/
├── manifest.json
├── world/
│   ├── pack.json
│   ├── holidays.json
│   └── translations/
│       ├── ru.json
│       └── en.json
├── russia/
│   ├── pack.json
│   ├── holidays.json
│   └── translations/
│       ├── ru.json
│       └── en.json
├── united_states/
│   ├── pack.json
│   ├── holidays.json
│   └── translations/
│       ├── ru.json
│       └── en.json
└── example_religious/
    ├── pack.json
    ├── holidays.json
    └── translations/
        ├── ru.json
        └── en.json
```

Это пример структуры. Можно адаптировать её к существующему проекту, но разделение метаданных, данных праздников и переводов обязательно.

Предусмотри возможность добавлять новые наборы, регионы, страны и религиозные традиции без изменения кода приложения.

### Манифест наборов

Создай `manifest.json`, содержащий список доступных наборов.

Для каждого набора должны поддерживаться:

- уникальный `id`;
- название набора через ключ локализации;
- описание через ключ локализации;
- категория: `world`, `country`, `region`, `religious` или другая расширяемая категория;
- путь к файлам набора;
- список доступных языков переводов;
- версия схемы данных;
- версия набора;
- источник данных;
- информация о лицензии данных, если она применима.

Не используй отображаемое название в качестве идентификатора набора.

### Метаданные набора

Пример `world/pack.json`:

```json
{
  "schemaVersion": 1,
  "id": "world",
  "nameKey": "pack.world.name",
  "descriptionKey": "pack.world.description",
  "category": "world",
  "version": "1.0.0",
  "dataFile": "holidays.json",
  "translationsDirectory": "translations",
  "availableLocales": ["ru", "en"],
  "source": {
    "name": "Example source",
    "url": null
  },
  "license": {
    "spdxId": null,
    "name": "Unspecified",
    "url": null
  }
}
```

Пример демонстрирует структуру, а не утверждает наличие конкретного источника или лицензии. Не указывай выдуманные источники и лицензии для реальных данных.

### Формат праздников

Пример `world/holidays.json`:

```json
{
  "schemaVersion": 1,
  "holidays": [
    {
      "id": "new_year",
      "nameKey": "holiday.new_year.name",
      "descriptionKey": "holiday.new_year.description",
      "dateRule": {
        "type": "fixed",
        "month": 1,
        "day": 1
      },
      "durationDays": 1,
      "tags": ["public", "international"],
      "enabledByDefault": true
    },
    {
      "id": "easter_example",
      "nameKey": "holiday.easter.name",
      "descriptionKey": "holiday.easter.description",
      "dateRule": {
        "type": "calculated",
        "calendar": "gregorian_easter"
      },
      "durationDays": 1,
      "tags": ["religious"],
      "enabledByDefault": false
    }
  ]
}
```

Не ограничивай модель данных только фиксированными датами. Предусмотри расширяемую систему правил дат:

- фиксированная дата;
- N-й день недели определённого месяца;
- смещение относительно другой даты;
- вычисляемая дата по поддерживаемому календарному алгоритму;
- ежегодные и разовые праздники;
- продолжительность праздника;
- при необходимости исключения для конкретных лет.

Не реализуй поддержку всех мыслимых календарей заранее, но создай архитектуру, позволяющую добавлять новые вычислители дат без изменения формата всех существующих наборов.

Для вычисляемых дат используй явно указанный алгоритм и календарь. Не подменяй неизвестные правила приблизительными вычислениями.

### Переводы праздников

Переводы должны храниться отдельно от списка праздников.

Пример `world/translations/ru.json`:

```json
{
  "locale": "ru",
  "strings": {
    "pack.world.name": "Международные праздники",
    "pack.world.description": "Подборка международных памятных дат",
    "holiday.new_year.name": "Новый год",
    "holiday.new_year.description": "Начало нового календарного года",
    "holiday.easter.name": "Пасха",
    "holiday.easter.description": "Христианский праздник Воскресения Христова"
  }
}
```

Пример `world/translations/en.json`:

```json
{
  "locale": "en",
  "strings": {
    "pack.world.name": "International holidays",
    "pack.world.description": "A collection of international observances",
    "holiday.new_year.name": "New Year's Day",
    "holiday.new_year.description": "The beginning of a new calendar year",
    "holiday.easter.name": "Easter",
    "holiday.easter.description": "The Christian celebration of the Resurrection of Christ"
  }
}
```

Используй единый механизм разрешения ключей для интерфейса и наборов праздников либо два согласованных компонента с общей логикой резервирования переводов.

Отсутствующий перевод не должен приводить к падению приложения.

### Интерфейс работы с праздниками

Добавь экран, на котором пользователь может:

- просматривать доступные наборы;
- видеть их описание, категорию и доступные языки;
- включать и отключать отдельные наборы;
- одновременно использовать несколько наборов;
- просматривать праздники набора;
- просматривать праздники за выбранный год;
- импортировать выбранные праздники в системный календарь Android;
- выбирать календарь назначения, если это поддерживается текущей архитектурой;
- проверять количество событий перед импортом;
- подтверждать импорт;
- видеть результат операции и ошибки.

Не создавай дубликаты при повторном импорте одного и того же набора.

Для идентификации импортированных событий используй устойчивую связь с идентификатором набора и идентификатором праздника. Не полагайся исключительно на название и дату события.

Не удаляй пользовательские события при отключении набора. Отключение набора не должно автоматически очищать ранее импортированные события.

## 4. Модульный планировщик смен

Добавь отдельный функциональный раздел для пользователей, работающих по сменному графику.

Пользователь должен иметь возможность:

- задавать дату начала расписания;
- определять циклы работы и отдыха;
- использовать готовые шаблоны, например 2/2, 1/3, 3/3;
- создавать произвольные циклы;
- указывать время начала и окончания смены;
- задавать название события;
- выбирать период генерации расписания;
- при необходимости включать отсыпные дни и другие типы дней;
- предварительно просматривать результат;
- экспортировать расписание в ICS;
- импортировать расписание в выбранный календарь Android.

Не зашивай все графики в Kotlin-код: готовые шаблоны должны храниться в отдельных JSON-файлах и обнаруживаться автоматически через манифест.

Поддержи смены, переходящие через полночь. Корректно обрабатывай даты, часовые пояса и переходы времени.

Не создавай события без проверки входных параметров и предварительного просмотра.

## 5. Генератор ICS

Реализуй отдельный модуль генерации ICS на основе пользовательских параметров.

Предусмотри возможность создавать события с заданными:

- названием;
- описанием;
- датой и временем начала;
- датой и временем окончания;
- часовым поясом;
- повторением, если оно поддерживается;
- периодом генерации;
- дополнительными параметрами, допустимыми выбранной моделью данных.

По возможности используй общий механизм формирования событий для планировщика смен и наборов праздников.

Обеспечь корректное экранирование текста, форматирование дат и совместимость с RFC 5545. Не формируй ICS простой конкатенацией строк без учёта требований формата.

Проверь корректность переносов строк, экранирования специальных символов, уникальности UID и представления дат.

## 6. Массовое и полное удаление событий

Доработай существующие механизмы удаления календарных записей.

### Поэтапное массовое удаление

- Позволяй пользователю выбрать календарь.
- Предусмотри выбор событий по доступным критериям.
- Показывай предварительный список и количество выбранных событий.
- Удаляй события небольшими пакетами.
- Обрабатывай ошибки каждого пакета.
- Не считай операцию успешной, пока не получен результат выполнения.
- Не блокируй интерфейс на время операции.
- Показывай прогресс и итоговую статистику.
- Предусмотри безопасное продолжение или повтор попытки после частичной ошибки.

Размер пакета должен настраиваться внутри реализации и подбираться с учётом ограничений Android. Не полагайся на один огромный запрос удаления.

### Полная очистка

Добавь отдельную функцию очистки выбранного календаря.

Перед началом операции пользователь должен увидеть предупреждение о количестве записей и явно подтвердить действие.

Если приложение не имеет необходимых разрешений, запроси их штатным способом.

Не удаляй сам календарь, учётную запись или события в других календарях. Чётко разграничивай очистку событий и удаление календаря.

Учитывай особенности повторяющихся событий, экземпляров серий и ограничений провайдера календаря.

## 7. Темы оформления

Добавь выбор темы:

- светлая;
- тёмная;
- системная.

Выбор должен сохраняться после перезапуска.

Все экраны, диалоги, меню, элементы выбора и состояния ошибок должны корректно отображаться в каждой теме.

Если используется Jetpack Compose, реализуй централизованную тему через `MaterialTheme`. Если используется XML, адаптируй решение к текущей системе тем.

Не дублируй весь интерфейс ради поддержки тёмной темы.

## 8. Главное меню и организация интерфейса

Убери нагромождение действий на главном экране.

Сгруппируй функции по смыслу. Предусмотри доступ к:

- управлению ICS;
- управлению событиями и очистке;
- наборам праздников;
- планировщику смен;
- генератору ICS;
- настройкам;
- информации о приложении.

Выбери подходящую навигацию исходя из текущей архитектуры. Не добавляй отдельный экран ради каждой небольшой операции, если удобнее использовать диалог или вложенный раздел.

Опасные операции должны быть визуально отделены от обычных действий.

## 9. Настройки и хранение данных

Пользовательские настройки должны сохраняться между запусками.

Храни предпочтения пользователя отдельно от файлов исходных наборов.

Не изменяй файлы встроенных наборов при включении или отключении праздников.

Если потребуется хранить пользовательские наборы, их настройки или шаблоны, используй отдельное хранилище с понятной схемой.

Не добавляй базу данных только ради формальности: сначала оцени существующий механизм хранения и объём новых данных.

## 10. Open Source и лицензии

Подготовь приложение к открытому распространению.

Добавь:

- лицензию самого проекта, если она ещё не определена;
- актуальный список сторонних библиотек и их лицензий;
- описание источников и лицензий наборов праздников;
- README с назначением приложения, возможностями и инструкциями сборки;
- описание структуры проекта;
- инструкции по добавлению нового языка;
- инструкции по добавлению набора праздников;
- инструкции по добавлению шаблона смен;
- CONTRIBUTING.md с правилами внесения изменений.

Не придумывай сведения о лицензиях и происхождении данных. Если информация отсутствует, явно отметь её как требующую проверки.

Не включай в репозиторий секреты, токены, локальные настройки IDE, временные файлы и приватные данные календарей.

## 11. Тестирование

Добавь тесты для критически важных компонентов.

Обязательно проверь:

- загрузку корректного языкового JSON;
- обработку повреждённого JSON;
- отсутствие отдельных переводов;
- резервные переводы;
- обнаружение новых языков и наборов;
- проверку уникальности идентификаторов;
- расчёт фиксированных и вычисляемых дат;
- переходы между годами;
- високосные годы;
- генерацию смен, переходящих через полночь;
- формирование корректного ICS;
- экранирование специальных символов;
- уникальность UID;
- обработку ошибок при массовом удалении;
- отсутствие дубликатов при повторном импорте;
- сохранение настроек;
- переключение тем.

Для операций с реальным системным календарём используй инструментальные тесты там, где это возможно. Не ограничивайся тестами, которые проверяют только создание объектов без проверки результата.

## 12. Архитектурные требования

Разделяй следующие компоненты:

- локализация интерфейса;
- загрузка языковых модулей;
- каталог наборов праздников;
- загрузка и валидация данных праздников;
- вычисление дат праздников;
- планировщик смен;
- генератор ICS;
- взаимодействие с системным календарём;
- массовое удаление;
- настройки;
- навигация и UI.

Названия классов и пакетов выбирай с учётом существующей структуры проекта. Не создавай искусственные абстракции без практической необходимости.

Все операции с календарём должны быть изолированы от UI, чтобы их можно было тестировать отдельно.

## 13. Подготовка к публикации

Проверь возможность сборки релизной версии.

Подготовь документацию и конфигурацию проекта к публикации на GitHub, F-Droid и RuStore. Не утверждай, что публикация выполнена, если она фактически не проводилась.

Проверь зависимости на совместимость с требованиями F-Droid, включая возможность сборки из исходников без скачивания заранее собранных бинарных компонентов.

Не добавляй аналитику, рекламу, телеметрию или сетевые сервисы без явной необходимости.

Не меняй идентификатор приложения и подпись без веской причины, поскольку это может нарушить обновление уже установленной версии.

## 14. Порядок выполнения

Работай последовательно:

1. Изучи существующий проект и составь краткий перечень текущих функций.
2. Определи, какие компоненты можно переиспользовать.
3. Составь план изменений с учётом зависимостей между задачами.
4. Реализуй модульную систему языков.
5. Реализуй систему наборов праздников и переводы.
6. Добавь интерфейс управления праздниками и импорт в календарь.
7. Добавь планировщик смен и шаблоны графиков.
8. Реализуй генератор ICS.
9. Доработай массовое и полное удаление.
10. Добавь темы, меню и экран информации о приложении.
11. Подготовь документацию, сведения о лицензиях и тесты.
12. Собери приложение и исправь найденные проблемы.

Если весь объём невозможно безопасно реализовать за один проход, выполняй его поэтапно, сохраняя проект в рабочем состоянии. Не удаляй незавершённые функции и не заявляй об их готовности без проверки.

После каждого значимого этапа проверяй компиляцию и соответствующие тесты.

## 15. Критерии завершения

Работа считается завершённой, когда:

- существующие функции ICS продолжают работать;
- новые языки подключаются добавлением JSON-файла и регистрации в манифесте, если она предусмотрена;
- новые наборы праздников добавляются без изменения бизнес-логики;
- переводы праздников отделены от данных праздников;
- новые шаблоны смен подключаются через файлы данных;
- праздники и смены можно предварительно просматривать и импортировать в календарь;
- генератор создаёт корректные ICS-файлы;
- массовое и полное удаление безопасно обрабатывает ошибки;
- темы и выбранный язык сохраняются;
- интерфейс организован через удобное меню;
- документация описывает расширение модулей;
- сборка проходит успешно;
- критические сценарии покрыты тестами.
